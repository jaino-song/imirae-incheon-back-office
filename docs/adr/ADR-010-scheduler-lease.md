# ADR-010: Database lease decides scheduler ownership

Background work (message-trigger dispatch, eFormsign document jobs, auto-finalization, retention cleanup, agent sweeps, and the other `@Cron`/`@Interval` entry points) runs on exactly one backend host at a time. The host that runs it is the one holding a single-row lease in the production Postgres, not the one that DNS or an environment file happens to point at. This is the first prerequisite named in the BJJ-298 failover decision: automatic AWS → LightNode failover is only safe once scheduler ownership cannot split.

## Context

Since 2026-09-02 `main` deploys to whichever host `api.babyjamjam.com` resolves to (Lightsail or the LightNode fallback), and both hosts share one Postgres. Before this decision, ownership of background work was decided only by environment variables (`SCHEDULERS_ENABLED` and the per-feature gates) that are fixed per host in Compose or `backend.env`. That is correct while an operator flips exactly one host at a time, and it is exactly what an automatic failover cannot guarantee: a partial AWS outage in which the instance is alive but unreachable from outside would leave Lightsail's schedulers running while the fallback is promoted, and two hosts would send messages and finalize documents for the same rows.

Every unit of work already has a row-level fence (`message_trigger_job.claim_token`, `eformsign_document_job.leaseToken` with heartbeat, `auth_email_outbox` `FOR UPDATE SKIP LOCKED`, the PWA digest claim token, agent action compare-and-swap). Those fences bound duplicate side effects; they do not stop two hosts from racing for the same work and doubling database load and provider traffic. The Valkey locks used by the eFormsign reconcile sweep and the agent action sweep are per host and cannot arbitrate across hosts. What was missing was one host-level gate above all of them.

## Decision

- **One table, one row.** `scheduler_lease` holds the row `background-owner` with `holder_id`, `instance_id`, `acquired_at`, `renewed_at`, `expires_at`. Acquire and renew are the same statement: `INSERT … ON CONFLICT ("name") DO UPDATE … WHERE … RETURNING`. Zero rows returned means another holder owns a live lease. The statement is self-healing (no seeded row is required) and is never wrapped in a transaction; the production connection runs through pgbouncer with a small pool.
- **The database clock is the only clock.** Expiry, renewal age, and takeover are all judged with `now()` inside the statement, so the two hosts' wall clocks never matter (the LightNode host runs at UTC+8, Lightsail at UTC).
- **Holder identity is the host, instance identity is the process.** `SCHEDULER_LEASE_HOLDER_ID` is fixed per host (`lightsail`, `lightnode`); a random `instance_id` is generated per process. The same holder may renew freely with the same instance. A different instance of the same holder (a recreated container) may take over only after the previous instance has not renewed for 70 s. That is deliberately longer than the 60 s local hold grace below: a stalled predecessor stops believing it holds the lease before its successor can be admitted, so an old and a new process never both believe they hold the lease during a deploy.
- **Parameters.** TTL 90 s, renewal every 20 s, and a process considers itself the holder only while its last successful renewal is less than 60 s old (monotonic clock). Two consecutive failed renewals are tolerated; the third is not. A renewal that returns zero rows drops ownership immediately. A renewal round trip that has not settled after 15 s is treated as failed so a black-holed connection can never wedge the renew loop; a stale result arriving later is ignored.
- **A host with schedulers disabled never contends.** When `SCHEDULERS_ENABLED=false` the service is in `standby`: it never writes to the lease table and reports itself as not holding. Without this rule the always-on passive fallback would take the lease from Lightsail and nobody would run background work. Consequently the existing environment gates stay in place and the lease is an additional AND condition, not a replacement.
- **Modes.** `SCHEDULER_LEASE_MODE=required` (the default when `NODE_ENV=production`) contests the lease. `off` (the default elsewhere) answers "held" without touching the database, for local development and tests. An unrecognized value is logged and falls back to the default; the lease must never prevent the HTTP API from booting.
- **Every entry point checks explicitly.** Each `@Cron`/`@Interval` method begins with `if (!this.schedulerLease.holdsLease()) return;`. Loops without a per-item database claim (contract auto-finalize, eFormsign reconcile, client due-date sync, notification cleanup) re-check per item and stop when the lease is lost. A source-scanning spec fails the build if any `@Cron(`/`@Interval(`/`@Timeout(` method anywhere in the backend package is not followed by a `holdsLease()` call before the next decorated method. A tick that is already running when the lease is lost finishes; the row-level fences bound whatever overlap that leaves.
- **Lifecycle.** The first acquisition is awaited (bounded) in `onModuleInit`, which completes before `@nestjs/schedule` mounts jobs in `onApplicationBootstrap`. On shutdown the process marks itself not-held first, waits (bounded) for any renewal in flight, then releases best-effort with a short timeout; an acquire that lands after shutdown began is released again rather than left naming a dead process. A shutdown that arrives while the startup acquire is still pending never starts the renew loop. `SchedulerLeaseModule` is imported directly after `DatabaseModule` so Nest's reverse-order teardown releases before Prisma disconnects.
- **Observable.** `GET /health/lease` returns `{ mode, holderId, held }`; the fallback operator's `status` prints `lease_mode=` and `lease_held=` from that endpoint. `SELECT * FROM scheduler_lease` shows the same truth to an operator with database access.

## Deployment

- `backend/env.tpl` carries `SCHEDULER_LEASE_MODE="off"` and `SCHEDULER_LEASE_HOLDER_ID="local"` for development.
- Both fallback Compose files set `SCHEDULER_LEASE_MODE: "required"` and `SCHEDULER_LEASE_HOLDER_ID: "lightnode"`; `contract.test.sh` asserts both keys in both files. The passive file keeps `SCHEDULERS_ENABLED: "false"`, so the passive runtime is in standby by the rule above.
- Lightsail reads its flags from the host `backend.env`. When AWS returns, add `SCHEDULER_LEASE_MODE=required` and `SCHEDULER_LEASE_HOLDER_ID=lightsail` there as part of the failback runbook (BJJ-298) before re-enabling its schedulers; until then Lightsail falls back to `NODE_ENV=production` → `required` with the container hostname as holder, which works but forfeits the same-holder fast takeover on container recreation.
- Preview (`SCHEDULERS_ENABLED=false`) is unaffected: standby, no writes.

## Consequences

- Two hosts with `SCHEDULERS_ENABLED=true` against one database are now safe: one runs background work, the other idles and reports `held=false`. Failover of scheduler ownership takes at most one TTL (90 s) after the previous holder stops renewing, and is immediate after a clean shutdown.
- A container recreate on the same host has a gap of up to 70 s if the old process could not release (crash), and no gap if it released cleanly. This needs a fixed `SCHEDULER_LEASE_HOLDER_ID`; a host that falls back to the container hostname is a new holder each time and waits the full 90 s TTL after a crash.
- The lease adds one small write per host every 20 s.
- The passive fallback still cannot take over schedulers automatically because its `SCHEDULERS_ENABLED` is false. Flipping the passive Compose to `true` and letting the lease alone decide ownership, and reworking the failover controller's passive-gate checks, are deliberate follow-ups, not part of this decision.

## Alternatives considered

1. **Postgres advisory lock** held on a connection. Rejected: state disappears with the connection, is invisible to operators, and is incompatible with pgbouncer transaction pooling.
2. **Valkey lease.** Rejected: each host runs its own Valkey; there is no shared instance, and adding one would add a second stateful dependency to the failover path.
3. **Rely on the per-row fences alone.** Rejected: they bound duplicate side effects but do not stop two hosts from racing for every job.

## Verification

Unit specs cover mode resolution, standby never touching the repository, acquire/renew/loss/grace transitions under fake timers, and shutdown release. A real-Postgres spec in the auth-e2e suite drives two repository instances through acquire, contention, renewal, same-holder takeover, release, and expiry. The drift spec enforces the entry-point rule. In production, while the fallback host is `temporary-active`, `curl 127.0.0.1:3101/health/lease` shows `held=true, holderId=lightnode` (a passive host shows `mode=standby, held=false` and never touches the row, so the rehearsal below does nothing there), and forcing the row to another holder (`UPDATE scheduler_lease SET holder_id='rehearsal', expires_at=now()+interval '3 minutes' WHERE name='background-owner'`) makes `held` false within one renewal and true again after expiry.
